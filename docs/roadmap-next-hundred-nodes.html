flograph's Next Hundred Nodes

The library is what makes it a tool. Here is what to build, and in what order.

Drafted this session · 20 nodes shipped alongside it · branch worktree-killer-nodes

01 — Thesis

The one seat nobody else is sitting in

Every data tool picks two of these four and gives up the rest: visual (you see and wire the pipeline), Python-native (the escape hatch is a real language, not a DSL), ships an app (the output is a dashboard a non-technical person opens), and local & free (one file, no account, no server, no seat cost).

KNIME is visual and ships an app but its scripting is bolted on and the good parts are paywalled. dbt and Dagster are Python-native and production-grade but there is no canvas and no dashboard. n8n is visual and local but it is an automation tool that treats a DataFrame as an exotic payload. Power Query is visual and everywhere and hits a ceiling the moment you need a join it didn't anticipate. Retool ships an app but the pipeline is someone else's SaaS.

flograph is the only one that takes all four. That is the wedge. The product vision — "what Excel should have grown into", a live dashboard handed to someone who will never open the canvas — is downstream of it.

Who it is for, in order

  • The ETL engineer who is tired of a repo of thirty clean_vendor_x.py scripts that only they can run. flograph makes the pipeline legible, the schedule real, and the handoff possible.
  • The analyst who lives in Power Query and has hit its ceiling — but does not want to become a programmer to get past it.
  • The jack-of-all-trades developer who wants one canvas for the daily plumbing: hit an API, reshape the JSON, diff two exports, load a table, post to Slack — without a new project skeleton each time.
  • The person the dashboard is for, who never sees any of the above.

The library is the product surface all four of them touch. A killer app here is a library deep enough that a real pipeline is built entirely from nodes, and the Python Script node is a choice, not a rescue.

03 — The gap

What stands between here and "killer app"

The transform and viz libraries are already strong — 20-odd transforms, a Plotly surface with every chart kind, KPI cards, slicers, reports, a wiki. The holes are not in reshaping data. They are in getting data in, keeping it trustworthy, running without a human, and shipping the result. Ranked by how much each blocks the core promise:

Connectors partly shipped

An ETL tool that can only read files it was handed is a reshaping tool. Shipped this session: SQL (any SQLAlchemy DB), DuckDB, HTTP, REST pagination. Still open: Google Sheets, cloud object storage (S3/GCS/Azure), warehouses as first-class (Snowflake/BigQuery auth), message queues, the SaaS long tail (Salesforce, HubSpot, Airtable, Notion, Stripe).

Automation & triggers partly shipped

A flow that only runs when you press play is a notebook. Shipped this session: Notify (Slack / email / webhook / ntfy), Shell Command, Wait for File, List Files. Still open: a schedule / cron trigger and a webhook trigger (these touch the engine), loop over rows / groups, and try / catch so a bad row does not kill the run.

Incremental execution

Re-running the whole graph on every change is fine at 10k rows and impossible at 10M. Needs partition-aware materialization: "this node's inputs for January have not changed, keep its cached output." The .flograph cache bundle already stores per-node output — this is the policy layer on top.

Observability & lineage

When a dashboard number looks wrong, the question is "what feeds it and when did it last refresh?" Needs: a run history, column-level lineage ("this column came from that join"), freshness stamps, and row-count / schema deltas surfaced per run. The As-of stamp idea generalised into a system.

Reusability — metanodes

Right now a 12-node "clean a vendor file" subgraph is copied and re-wired for every vendor. A metanode — a subflow that presents as one node with its own ports and params — is the single biggest multiplier for how fast a real pipeline gets built. Parked in ideas_archived.md #4; it should be un-parked.

The last mile — deploy

flograph run and .flowf are the seed. The finished form: publish a flow as (a) a scheduled job, (b) a REST endpoint that runs the graph on request, (c) a read-only dashboard URL. That is what turns "I built a flow" into "I shipped a tool".

05 — Bigger bets

Seven moves that are not nodes

Nodes widen the tool. These deepen it — each is an engine or UX investment that changes what a flograph project can be. Roughly in leverage order.

1 · Metanodes / subflows

A selected subgraph collapses into one node with derived ports and a parameter surface you define. Reusable, nestable, shareable. The highest-leverage single feature for building real pipelines fast — and the precondition for a node marketplace of flows, not just scripts.

2 · Incremental execution & materialization

Per-node, per-partition cache validity: "inputs for this slice are unchanged, skip." Turns flograph from a thing that works at demo scale into a thing that runs a nightly 50M-row load. The cache bundle already persists outputs; this is the invalidation policy and a partition key on sources.

3 · Deploy targets

One flow, three publish buttons: scheduled job (cron, runs headless, notifies on failure), REST endpoint (POST a payload, get the graph's output), shared dashboard (read-only URL, auto-refreshed). flograph run + .flowf are step one of five.

4 · Data contracts on ports

A port can carry a schema, not just a type. Wire-time check: does the upstream frame satisfy the downstream node's expected columns? Catches the break when a vendor renames a field — before the run, at the wire.

5 · Lineage & freshness

Every run recorded. Column-level lineage: click a dashboard number, see the nodes and source columns behind it. Freshness SLAs per source with a visible breach. This is what makes a handed-over dashboard trustworthy without the builder in the room.

6 · A node registry

User nodes exist; make them shareable. flograph add stripe-connectors pulls a versioned bundle of node scripts (and, post-metanodes, whole flows) from a gallery. Community fills the SaaS long tail faster than any roadmap can.

7 · Environments

Named configs — dev / staging / prod — each a set of variable + secret values. Run the same flow against any of them; the deploy target picks one. Extends the shipped flow-variables + .env work.

+ · Collaboration

Opt-in git per project (every save a commit — ideas.md L1), then comments on nodes and presence. Lower priority than the six above, but it is where "a tool I use" becomes "a tool my team uses".

06 — Sequencing

Three horizons

Build order is not priority order — it is dependency order plus "what unlocks a demo you can show". Each horizon should end with a story you can tell.

Horizon 1 · now – next

Close the ETL loop

  • Connectors: Sheets, cloud storage, SFTP
  • Automation nodes: Notify, Watch Folder, Wait for File, Shell, Try/Catch
  • Analyst transform batch (period math, ranking, bins) + Schema Contract
  • Viz context cards + User Form

Story: a nightly vendor feed — watched, validated, loaded, reported, and Slacked — built without one Python Script node.

Horizon 2 · the multiplier

Metanodes & scale

  • Metanodes / subflows
  • Incremental execution + partition keys
  • Schedule & Webhook triggers (engine work)
  • AI: Embed, Semantic Join, RAG Retrieve

Story: one "clean a vendor file" metanode, reused across 20 vendors, re-running only the month that changed.

Horizon 3 · the product

Ship & share

  • Deploy targets: job, REST endpoint, dashboard URL
  • Lineage, run history, freshness SLAs
  • Node / flow registry + flograph add
  • Environments; opt-in git collaboration

Story: an analyst publishes a self-serve dashboard from a canvas, and never touches a server.
