# Changelog

## 0.1.9

| Category | Change | Details |
| --- | --- | --- |
| Feature | Flow-level variables: name a value once, use it anywhere | A new **Variables** node (Util) names values one `name = value` per line, and any text box in the Properties panel can then say `${name}` — a file path, a filter query, a sheet name, a chart title. Change the value in one place and every node that reads it re-runs. Scripts read the same names through `ctx.vars`. Values can also come from data: wire a dict into the node's `values` input or a table into `table` and a config file or a slicer drives the flow. This is not a lookup bolted onto the side — a `${name}` becomes a **real edge in the graph**, the same kind the Goto/From links already use, so run ordering, re-runs, loop rejection and cached-result invalidation all behave exactly as they would with a wire drawn between the two nodes. Without that, a node whose path reads `${region}` would have hashed identically for every region and quietly served the wrong cached table. |
| Feature | Secrets live in a .env file, not in the project | `${env:NAME}` in any text box reads from a **.env file managed under Tools ▸ Secrets…** — choose an existing file or create one, and the project stores only its *path* (relative to the project where it can be, so a team can each keep their own copy in the same spot). Values never enter the .flograph file, which until now stored a password typed into a node in the clear and carried it to whoever you sent the project to. The dialog masks values by default, shows how many nodes use each key, and lists keys a node asks for that the file hasn't got. Results computed from a secret are never written to the on-disk cache. |
| Feature | `--var` turns a flow into a parameterisable job | `python -m flograph.engine.headless flow.flograph --var region=North` overrides what the Variables node declares, so one canvas runs per region or per date from a scheduler with nothing edited in between. A name the flow doesn't declare stops the run rather than being ignored — a silent typo that ran the default would be worse. |
| UI | The run progress bar is a thin line at the head of the run's message | The bar was drawn at the full default control height, which made it the tallest thing in the status bar and set the height of the whole strip. It is a **short 80×8 track** now, and it has moved from the far right to the **bottom left, immediately ahead of the run's own message** — `▬▬▬▭▭  Running Read Excel · node 3 of 12` reads as one line rather than as a widget at one end of the window and the words at the other. Getting it there meant the window owning its status text as a widget: Qt paints a status-bar message from the left edge, straight through anything parked there, so the bar could not have shared the space otherwise. The status bar itself loses the extra height it was carrying, run or no run. |
| Feature | A busy machine makes the app slower, not dead | Running eight branches at once is a good idea right up until there isn't room for eight branches' worth of data, and past that point the old behaviour was to keep starting them until the machine gave out. A run now **watches how much memory is actually free and runs fewer nodes at once when it is running short** — half as many when things are tight, one at a time when they are nearly gone — and opens back up as soon as there is room. It reads **free memory, not the percentage in use**: 85% of a 128 GB machine is 19 GB still free and nothing is wrong, while the same percentage of a laptop is nothing left, so a big machine is never held back for looking busy. A worker count you have set yourself in Settings is honoured until things are genuinely critical, on the grounds that someone who chose a number meant it. This matters most for a flow you have handed to somebody else: they cannot act on advice about worker counts, but "it went slower" is something anyone can live with. |
| Feature | The memory warning appears when it is any use | It used to be **suppressed during a run** — the one time the flow is actually filling the machine up — because the status line was busy saying what was running. It is carried on that line now instead of being thrown away. Under pressure the **steps holding the most are marked on the canvas** in the same amber as a stale pin, because "which step is doing this" is the part you can act on: it is the node to put a **Max rows** on, or to filter earlier. And the wording no longer assumes you built the flow — it leads with closing other applications and reading fewer rows, and keeps the settings advice for afterwards. |
| Feature | Max rows on Read Parquet and Read SQLite | Working against a slice of something large is meant to be a deliberate choice made at the step that reads the data, and Read CSV, Excel and JSON already had it — the two where the big files actually live did not. Read SQLite turns it into a **`LIMIT` in the query** when reading a whole table, so the rest is never fetched; in query mode the SQL is yours, so the rows are trimmed after it runs rather than by wrapping a statement that may not survive it. Read Parquet trims after reading too, since pandas' Parquet reader takes no row limit — Columns and Row filters are still the ones that make the read itself cheaper, and the node's help says so rather than implying otherwise. |
| Bug Fix | Cards let go of data the run had finished with | `setModel()` does not delete the model it replaces, so every re-fed table card — on the canvas or a dashboard tile — kept the **previous run's frame** alive until the card itself was destroyed. On a live dashboard re-running on every slicer change, that was the leak that mattered: memory climbed with each refresh and never came back. Fixed, along with four more of the same shape: the inspector's tabs were detached rather than deleted (and one closure held a whole table), **Reset Caches** left every card displaying — and pinning — the values it had just discarded, deleting a node left its webview renderer and table model alive until the app closed, and **New/Open** never emptied the engine cache, so a new project inherited every frame the last one held. Webviews now destroy their renderer when cleared rather than navigating away from the page, since a renderer's memory stays at its high-water mark otherwise. |
| Feature | Opening a project no longer loads its results | Opening used to unpickle **every** cached result before you had asked for anything. On a project holding a few large tables that is gigabytes: a 14-node flow with 2M-row frames cost about **4 GB of memory just to open**, and duplicating such a flow was enough to exhaust the machine before Run had been pressed — on a Linux box with compressed swap, enough to take the whole desktop with it. Opening now reads **one manifest file and allocates nothing**. Each node still counts as cached and clean; its value is fetched when something actually needs it — the engine warms a run's inputs on a background thread before the first node starts, and looking at a node, exporting a report or opening a dashboard loads that one value. Measured on a real 899 MB project cache: **8.3 s and 3.3 GB, down to instant and nothing**. The trade is visible in one place: **node cards on the canvas come up without their table previews** until you run or click into them, because the canvas is the one view whose node count has no upper bound. |
| Feature | Cached tables come back smaller than they went in | A cache blob written by an older pandas holds its text as individual Python strings — about **80 bytes for a 29-character email address**. Restoring one now re-lays it out into an Arrow buffer, which is the same data, the same type and the same treatment of missing values, in **a third of the space**. On the same 899 MB project that is **3.3 GB down to 1.8 GB** if you load the lot. Only the layout changes, and only on the way in off disk: a value a node has just computed is left exactly as the node produced it. Needs pyarrow (the `parquet` extra); without it, nothing happens. |
| Fix | "MemoryError: " now says what to do about it | A node that ran out of memory reported literally `MemoryError: ` — a colon promising a detail that never came, because Python raises it with no message. It now names the thing that happened and what can be done about it: filter earlier, lower **Nodes to run at once**, or reset the caches. The error formatter was also hardened against running out of memory *itself* while formatting, which would kill the worker thread without reporting anything and leave the node stuck on **Running** forever. |
| Fix | Saving no longer needs twice the memory of the biggest thing in the project | Each cached result was serialised into memory in full and only then written to disk, so saving a 6 GB cache briefly wanted 12. It is streamed to the file now. Saving a project whose results have not been loaded also no longer loads them — it keeps the blobs it already has, which makes saving a large project markedly faster, and **Save As** copies them across rather than dropping them. |
| Feature | Fold a frame down to a single node | A frame was a backdrop, so a big flow was every node it contained, all the time. Click the **chevron in a frame's title bar** (or **right-click > Collapse frame**) and it folds into one **60x60 square** wearing the same chrome an ordinary node does — **name above, status light below** — so a block of work reads as a step in the flow rather than as a region of it. Where a node draws its mark, a folded frame draws **a 3x3 grid of the same status lights, one per node inside, in the order they run**: press F5 and you watch the flow light up through the closed lid, each cell filling as a pie exactly as a node's own LED does when it reports progress, and pulsing when it can't. More than nine and the grid **scrolls once the run passes the middle of it**, with a **+n** in the first cell counting what has already gone by; cells never move within the window, so a light can always be traced back to the node it belongs to. The frame's own light underneath fills by **how many of its nodes are finished**, turns red the moment any of them fails, and hovering it says the counts. **Wires that cross the boundary are not hidden** — they are real edges and pretending otherwise would misstate what the flow does — so each one grows **a pin on the box** and terminates there, one pin per wire, labelled with the node and port it stands for when you hover it. Those pins are **live**: drop a wire on one and it connects to the node inside, drag one out and it wires onward, without expanding anything. A wire running between two folded frames gets a pin on each. A folded frame **occupies only the box you can see** — it claims no hidden region — so you can park it anywhere without it quietly absorbing whatever it lands on, and dragging it carries **exactly what was inside when it folded** and nothing else. **Expanding restores the region around it wherever it now sits**. If nothing has moved in the meantime it grows back into exactly the space it vacated and **the canvas is left untouched** — fold and unfold as often as you like without your layout creeping away. If something has been parked in the way, room is made for it the way inserting space would: draw a line straight down from the folded square's bottom-right corner and everything beyond it slides right **together, by the same amount and no further than it has to**, landing clear of the frame rather than flush against it, so a row arrives with its spacing and alignment intact instead of fanned out with the far end flung twice as far; anything below in the frame's own column slides down instead. Nothing to the left or above is ever touched, **folding again takes the displacement back off**, wherever things have got to since — move one of them yourself in the meantime and it keeps your move, just without the shift on top, so the canvas never half-restores — and one **Ctrl+Z puts the frame and its neighbours back together**. A frame reopening inside another **stretches its parent to fit** rather than shoving it aside. And a frame drawn *around* existing frames arrives **behind** them rather than on top, so the frames you just grouped are still the ones you can click. **Copy and paste takes the whole nest**: a frame you copy brings any frame inside it, folded or not, and whatever those hold however deep it goes — the copies stand in for each other rather than for the originals, and a folded one arrives folded and still knowing the size it opens back to. Saving to the library goes the same way, so a component can be a frame of frames. Frames sitting inside the one you fold are folded away with it, "Run frame" reaches everything the frame holds, including the nodes inside any frame folded away within it, and the whole thing is saved with the project and goes through undo. |
| Feature | Save a frame to the library and reuse it | A frame and everything in it can be written to the node library — **right-click > Save as component…** — and it appears under **User Frames**, alongside your saved nodes. Drag it onto any canvas, or double-click it, and a **copy** arrives: fresh ids, independent of the file, so editing it never writes back and editing the file never disturbs flows already using it. What it does keep is **where it came from**. Edit the library version later and a copy **nobody has touched** offers *Update from component* on its right-click menu; one you have edited shows the entry greyed out and says why, because an update would throw that work away. Taking the update rebuilds the contents from the file and **re-makes the wires reaching in from outside**, matched by the node name and port they were joined to — every id inside a component is regenerated, so a name is the only thing that can carry across — and it says so if a wire's node is gone from the new version rather than dropping it in silence. Whether a copy counts as edited is worked out by **hashing what it actually contains**, ignoring ids and positions, so moving it or pasting it doesn't count and changing a parameter, a script or a wire does; there is no per-node bookkeeping to get out of step. All one undo step. |
| Performance | Independent branches run at the same time | A flow that fanned out into four branches ran them **one after another**, however many cores were sitting idle and however much of the time was spent waiting on a file or a web request. Nodes now start as soon as their own inputs are ready, several at once, so a wide graph takes about as long as its slowest branch instead of the sum of all of them. Order is still exactly the order the wires describe — a node cannot begin until every node feeding it has finished, so a chain runs in strict sequence as it always did and only genuinely unrelated work overlaps. Nothing about a flow needs changing to get this. **Settings > General > Nodes to run at once** sets the limit; **Auto** takes it from the machine's cores, capped at 8 because the binding constraint on a real flow is memory, not cores — every branch in flight is holding its own intermediate data. Set it to **1** for the old one-at-a-time behaviour. Several node LEDs now light at once and the status bar says "Running 3 nodes" while they do, going back to naming the node whenever there is only one to name. **Cancel stops all of them.** |
| Feature | An example that shows the branches overlapping | **File > Open Example > Parallel Branches** is six independent branches hanging off one Start, each a Fetch feeding a Summarize. Press F5 and the six status lights come on together, rings filling, with *Running 6 nodes* in the status bar; it finishes in about **1.2s**. Set **Nodes to run at once** to **1**, mark everything dirty and run it again and the same flow takes about **6s** — the whole point, in one before-and-after you can time. Inside a branch the order still visibly holds: a Summarize only lights once the Fetch above it has gone green. The steps wait on the clock rather than on a real file, which keeps the example honest about the shape without shipping a big dataset to make a point about scheduling, and a note on the canvas says so. A test asserts the example really does reach six at once, so it cannot quietly stop demonstrating the thing it exists for. |
| Feature | A node can insist on running alone | Not all code is safe beside other code — matplotlib is not thread-safe, and a node writing a file or holding a device wants the process to itself. A node script declares `NODE["exclusive"] = True` and the engine drains whatever is in flight, runs it on its own, and only then carries on. The two matplotlib nodes (**Show Plot**, **Chart per Value**) ship with it set, so existing flows are safe without anyone needing to know this exists. For a node you have written or forked, **right-click > Run on its own** forces it either way for that one node; it is saved with the project and goes through undo. Leave it alone and the node follows whatever its code says, so editing the script later still decides it. |
| Fix | Output can't land under the wrong node | `print()` writes to a stream shared by the whole process, which was harmless while one node ran at a time and would have become a real bug the moment two did — a line printed by one node could surface in the log under another's name, which reads as that node misbehaving. Output is now routed by the thread that wrote it, so every line reaches the node that printed it however many are printing at once. Anything printed by something that isn't a node still goes where it always went. |
| UI | The run timeline shows what overlapped | The statistics window's timeline draws one bar per node against the run's wall clock, so nodes that ran together line up vertically and a flow running wide reads as a block instead of a staircase — no new chart, the existing one just had its axis pinned to the clock rather than to the sum of the node times, which would otherwise have squashed a fast parallel run into the left margin. The summary line says how much time the overlap saved and how many nodes were running at the peak. Per-node memory peaks are honest about sharing: a process-wide reading cannot be split between the nodes causing it, so each is charged the whole peak and the record notes how many were sharing it. |
| UI | Ordinary nodes are a square now | A node with nothing to show — a Sort, a Join, a Read CSV, anything with no card — was a 170px-wide box whose *height* changed with its port count, so a row of them read as a row of differently-sized rectangles rather than as a pipeline. Each one is now a **fixed 60x60 square** carrying a mark, with **the node's name above it** and its **status light below**, connectors either side as before: the shape most node-graph tools give a node that is only a step. **The size never varies**, whatever the port count: pins are centred on the box while they fit — three do exactly — and a node with more than that runs the rest out of the bottom and onto the canvas rather than growing, the way card nodes always have. So a Read CSV, a Sort and a Join are all the same box, and the canvas gets about two and a half times denser horizontally. Charts, tables, KPIs, notes and every other card are **untouched**: their content is the point of them, and a chart squeezed into 60px is a chart of nothing. The square has no header strip to print port names in, so those move to the **floating name pills** cards have always used (Settings > Canvas > Show port names, or per node on the right-click menu) — with two pins a side, position already tells them apart. Double-clicking the **name** renames, double-clicking the **square** opens the code, which is the header/body split relocated rather than a new rule to learn. **Settings > Canvas > Compact nodes** turns it off for the old wide box. Existing projects open unchanged: a node's saved position is still the top-left of its body, so nothing moves — the graph just gets airier. |
| UI | One Appearance dialog instead of six menu entries | Colour, mark, shape, port names, port collapsing and the canvas preview were six separate items on a node's right-click menu — half of them conditional, so the menu changed shape depending on what you right-clicked, and none of them were findable by anyone who hadn't already found them. **Right-click > Appearance…** is all six, grouped. It applies **live**, so the node changes behind the dialog as you choose and there is nothing to confirm; five of the six behaved that way from the menu already. Each change is its own undo step, except that trying marks on for size merges — clicking through sixteen swatches to settle on one is a single Ctrl+Z rather than sixteen. A colour deliberately does *not* merge: it arrives through a modal picker, so each one is already a single act, and resetting to the theme default deserves its own step back. |
| UI | Switch one node between the two shapes | The compact square is a canvas-wide setting, but the odd node wants to be the exception — a Python Script whose name is the only thing telling you what it does, say. **Appearance… > Shape** pins that one node to *Compact square* or *Wide box* and leaves everything else alone; *Canvas default* hands it back. Tri-state, exactly like the per-node port-names override: a node nobody has singled out keeps following the setting, so flipping the global still does what you expect to the rest of the graph. Saved with the project and on the undo stack. |
| Feature | Hold a key to see every port name | Port names are off by default because on a busy canvas they are noise, but the moment you are wiring something you want all of them. **Hold Q** over the canvas and every port name appears; let go and every node returns to exactly what it was showing — the setting, or its own override if it has one. Nothing is written down: it is a look, not a change. A plain key rather than a modifier, because Alt belongs to the menu bar on both Linux and Windows and binding it here would mean either swallowing that or watching the menu bar flicker into focus on every tap. Rebindable under **Settings > Canvas**. The release is guarded three ways — losing focus, the pointer leaving, the window deactivating — so a key-release swallowed by a popup can't leave the names stranded on screen. |
| Feature | Double-click opens what you want it to | Double-clicking a node has always opened its **code**, which is the rarer errand — nine times out of ten you want its **parameters**. That is the new default, and **Settings > Canvas > Double-click a node opens** takes Properties, Code or Rename. A node's *name* always renames whatever the setting says, since that is what a label is for, and notes and buttons always open their properties because their text is a parameter rather than code. |
| Feature | A node's properties and code in a window of their own | **Ctrl+double-click** any node (or **Open in Window** on its right-click menu) and its Properties and Code open in a floating window with a tab each. **Several can be open at once**, one per node — which is the point: the docks show whatever is *selected*, one node at a time, so comparing two nodes' parameters or keeping a script visible while editing the node that feeds it meant clicking back and forth and losing your place. Ordinary windows, deliberately — not always-on-top, not tool windows — so they stack with everything else. The title follows a rename, the window closes if the node is deleted, and a value still being typed in one lands before a run reads it. The same node twice is not offered: a node's unsaved-code marker is single, unowned state, and a second editor loading a clean copy would quietly clear the first one's. |
| Feature | Marks in the node library | Every row in the library tree and the Tab search popup now carries the mark the node will wear on the canvas, so a node is recognised in the list by the shape you then look for in the graph. Same drawn paths, rasterised once per mark and cached. |
| Feature | Give a node its own mark | The square shows a mark drawn from the node's **category** — a sheet for IO, exchanging arrows for Transform, a slider for Input, bars for Viz, angle brackets for Scripting. That is deliberately coarse: the name sits directly above the square and is the thing that actually tells a Sort from a Join. When it matters, **right-click > Appearance…** gives one node something else — a grid of sixteen drawn marks (funnel, Venn circles, database cylinder, ascending bars, rotation, …), **up to four characters of your own text**, so the Constant holding a year can just say `2024`, or **a picture of your own**: a PNG, JPEG, SVG or **animated GIF/WebP** that fills the square. A picture travels *inside* the project file as base64, so a flow you send someone arrives with its marks intact rather than pointing at a folder they don't have; a still is scaled to 128px and re-encoded on the way in, which turns a 1200×900 photo into about a kilobyte. An animation is kept byte-for-byte, Qt having no GIF writer, and is size-capped with a message that says so. Animated marks play, and stop when nobody is looking — zoomed out past the detail threshold, or with the node's canvas preview off — the same discipline image cards and reports already follow. The choice goes through undo and is saved with the project. The marks are **drawn, not typed**: the emoji and symbol characters this would obviously have used paint *nothing at all* on a machine whose interface font lacks them, and `QFontMetrics.inFont()` cheerfully reports otherwise — the same trap the Visuals list fell into. A test paints every mark and counts its ink. |
| UI | A maximized tile fills the page properly | Maximizing a chart, a KPI or a picture left it sitting in the middle of the page with a strip of canvas showing all the way round, its rounded corners cutting four notches out of the edge, and a resize grip in the corner that did nothing — a maximized tile is sized by the window, so dragging it was already refused. Maximizing a **Table** never looked like that, because it takes a different route internally. Both now land in the same place: flush to the edges, square-cornered, no grip, and the content runs right to the bottom. The title bar stays, since it carries the name and the way back out. |
| Performance | Zooming a card no longer re-runs it | **Scale %** on Show Plot, Show Plotly, Show Web, Show Table, Table Spec and Image marked the node dirty, so nudging a card's zoom put it — and everything downstream of it — back in the queue to produce exactly the figure, table or picture already cached. No node's `run()` has ever read the param: the zoom is applied to the card, after the fact. It is declared **cosmetic** now, so zooming redraws and nothing re-runs. A test sweeps the registry for the param rather than listing the nodes, so one that grows a Scale % later has to make the same call deliberately. |
| Feature | Scale % on the Chart per Value nodes | The six other Viz nodes had a **Scale %** and the two stack nodes didn't, so the one card most likely to hold more than fits was the one that couldn't be zoomed out. Both take it now, 25–400%: below 100 the charts draw smaller and more of the stack fits on the card, above 100 they draw larger and you scroll. It changes how much you see, not how big the card is — Width and Height still do that. Unlike on the single-chart nodes it is marked **cosmetic**, so zooming re-draws without re-running the split; a Plotly stack zooms through the embedded browser, so it stays crisp instead of being magnified. |
| Feature | Pin the Y axis on a Chart per Value | Both Chart per Value nodes take **Min Y** and **Max Y**, so a stack of charts can be read against a scale you chose rather than one derived from the data. Leave either blank to pin only the other end — a Min Y of 0 with the top left free is the common case, and the one **Same Y scale** could never give you. A pinned bound is used exactly as typed, with none of the 5% headroom a derived scale adds, so 0 means the axis sits on zero. They work with Same Y scale **off** too: each chart is still scaled to its own rows, but the end you pinned holds across all of them. Blank is the default, so nothing changes until you ask. (Box, violin and histogram work out their own value axis, so those take a *pair* of bounds or nothing.) |
| Feature | Find a node by name | **Ctrl+F** on the canvas (or **Edit > Find Node…**) opens a small search box in the corner, and typing narrows the list of nodes as you go — the answer to a flow that has grown past one screen, where the only way to reach a node was to remember roughly where you put it. A node is matched on **its own name first and its type second**, so "constant" still finds the Constant you renamed to "Tax rate", while a node actually called "Constant" outranks it. Moving through the list with **↑/↓ takes the canvas with you**: each node is selected and centred as you arrive, so finding it and looking at it are one gesture rather than two — and from far enough out the view **zooms back in** on the way, because centring alone lands on the flattened smudge a zoomed-out node is drawn as. That is safe because leaving is free: **Esc puts the view back exactly where it started**, zoom included, and **Enter** keeps the node and closes. The box sizes itself to the hits, collapsing to a single line when nothing matches. The canvas keeps its own Ctrl+F separate from the code editor's find, so which one you get depends on where you are typing. |
| Feature | Draw a Goto/From link when you want to see it | A named link is a wire the canvas deliberately doesn't draw — that is the whole point of the node — but when two cards sit three screens apart, the glow that says "there is a partner somewhere" can't say *which one, and where*. Right-click either card and pick **Show Link Lines** (a From offers **Show Link Line**, having only the one) and the canvas draws a dashed arrow from the Goto to each From reading it, pointing the way the value travels. It is per link and **off by default**, so one confusing pair can be traced without the canvas going back to the plate of spaghetti the links were introduced to avoid; either end can ask, so a single From can draw its own line without lighting up every other reader of the same Goto. The line is drawn, not wired: it can't be selected, cut or dragged, it sits under the real wires where the two cross, and one Ctrl+Z puts it away. There is a **Show link lines** tick in the properties panel too, and the choice is saved with the project. |
| Feature | The Visuals list is sorted, and shows you what a visual looks like | The panel beside a dashboard page listed its visuals in the order the nodes happened to be created — the one ordering nobody can search by. It is **alphabetical** now, one flat case-blind run, so a visual is found by the name it was given. (It was briefly grouped by kind as well; that meant knowing which group a visual fell into before you could find it, which is the opposite of the point.) Each row carries a mark saying which kind it is — plain geometric shapes rather than the emoji they used to be, which drew as *nothing at all* on a machine whose interface font has no emoji in it. **Rest the cursor on a row** and a small picture of the visual appears beside it, so the chart can be picked by looking at it rather than by remembering which name it was given. The picture is not a mock-up — it is a real tile, built for that node and thrown away — so it shows exactly what dropping the visual produces, down to "Run the flow to populate this tile" when nothing has run yet. A **Plotly chart is drawn too**, through the same snapshot the report pages use, so an interactive chart previews as the picture it would print as; it says "Drawing the chart…" while the browser takes it, and the picture is cached, so the second look is instant. |
| Feature | Images on the canvas | A new **Viz > Image** node shows a picture on the canvas — PNG, JPEG, **animated GIF and WebP**, SVG, BMP, ICO, TIFF and the rest of what Qt reads, with no extra packages to install. Three ways to get one in: **drag an image file** from the file manager onto the canvas and it becomes an Image node; **copy a picture to the clipboard and press Ctrl+V** (your OS screenshot key already puts one there, so that is the whole of "screen grab", and it works the same on Windows and Linux); or drop the node and pick a file. The card draws straight from the source, so the picture is there without running anything. **Fit / Fill / Stretch / Original size** plus a **Scale %** decide how it sits in the card, and "Card background" off drops the slab behind a cut-out PNG. Running the node emits the image on its `image` port with a ready-made `data_uri`, so it can go straight into a Plotly figure, an HTML view or a report. |
| Bug Fix | Crash when locking a page then dragging a Plotly chart | The app would go sluggish and then die. The page tab's right-click menu installed an event filter on the **whole application** for half a second, to swallow the follow-up context-menu event the platform sends after the menu has already opened. While it was installed, *every* event in the process went through Python — including the mouse-move and hover floods inside the chart card's embedded Chromium, which is both why dragging a chart felt like it was hanging and where it segfaulted. Two more faults in the same few lines: the filter object was created at import time, before the application existed at all, and it was removed by a timer owned by the tab bar, so closing a project could leave it installed for the rest of the session. All three are gone — the event is now accepted on the one widget it is actually delivered to. |

Elapsed only appears once a step has run for a second, because a stopwatch on a step that takes 200 ms is noise. And a node that has said nothing for ten seconds now says so, with how long it has been silent and a reminder that Cancel exists — `issues.md #4` recorded a chart node that "just sat in Running forever", where the problem was not the waiting but having no way to tell a hang from slow work. A node reporting progress or writing to the log is never called quiet however slow it is, and one that never spoke at all is worded differently from one that fell silent partway. The whole line is driven by a timer rather than by run events, deliberately: the two cases worth reporting — a slow node and a stuck one — are exactly the ones that send nothing at all. |
| Feature | A warning when cached outputs are why memory is tight | Every node's output stays in memory until something dirties it, which is what makes re-runs cheap — and on a big flow means the project can quietly grow until the machine starts swapping, with nothing said. The memory readout already knew the number and did nothing with it. It now turns amber when system memory is above 85% **and** cached outputs account for a tenth of the machine or more, with the heaviest nodes named in its tooltip and a one-off line on the status bar: `cached outputs are 9.0 GB of 32.0 GB, the largest being Read Excel Folder at 4.0 GB`. Both conditions have to hold — a machine at 90% is not this flow's doing if the flow holds 200 MB, and 12 GB on a 128 GB box is not a problem yet — because a warning that cries wolf is one you learn to ignore. It is said once rather than every couple of seconds, and stays quiet during a run, where the status bar has something more useful to say. Nothing is ever dropped automatically: a node is clean *because* its output is cached, so evicting one behind your back marks it dirty and it silently re-runs later — being told, and choosing what to freeze or reset, is the honest half of that trade. The nodes named account for aliasing, so a frame shared down a Goto chain is credited once, to whichever entry is really holding it, instead of sending you after a node holding nothing. |
| Feature | Create a desktop shortcut for the way you actually launch flograph | **File > Create Desktop Shortcut…** writes a real shortcut — a `.lnk` on Windows, a `.desktop` entry on Linux, a `.command` script on macOS — that starts flograph again exactly the way it is running now. That means the *interpreter*, not `python`: the shortcut names the venv's own executable by absolute path (`pythonw.exe` where there is one, so no console window trails the app), because a desktop launch inherits none of the environment a terminal or an IDE was giving it. It also means the right entry point, and the two are not interchangeable: a **one-file bundle** is pointed back at the `.py` the user was handed — never the temp directory it unpacks itself into, which is deleted the moment the app exits — while a **pip install** gets `-m flograph`. Which one you are on is worked out, not guessed: the bundle identifies itself by the payload it carries, and `-m flograph` is only used if a *fresh* interpreter, with this process's `PYTHONPATH` stripped out, can really import it; failing both, a checkout falls back to running its own `main.py`. If a project is open, the shortcut can carry it, so double-clicking opens flograph with that flow already loaded. The dialog shows the exact command and the exact file it is about to write before you commit to it, an existing shortcut of the same name is never replaced without being asked, and the icon is painted from the canvas's own palette — two nodes and the wire between them — rather than leaving a Python-file icon on the desktop. |
| Bug Fix | Long KPI values painted outside their card | A KPI shrinks its number to fit the space it has, but the size it picked came from an *estimate* of how wide the text would be — 0.62em per character, averaged. Bold digits, commas and currency symbols all run wider than that average, so a big enough number (a revenue total with separators, say) was sized to fit a box narrower than the one it was actually drawn in, and its ends were clipped off by the card's edges. The number that gets clipped is, reliably, the interesting one. The fit now measures the real advance width through `fontMetrics` and steps the font down until the text genuinely fits, on the canvas Card and the dashboard KPI tile alike. |
| UI | A multiline Text control fills the card you drag it into | The **Text** input control in multiline mode only ever claimed the height its box asked for, and left the rest of the card as dead space underneath — so dragging the node taller bought you a bigger empty margin rather than more room to write in, which is the one reason anybody drags that node taller. The box now takes every pixel the card gains. Single-line Text is deliberately unchanged: it stays pinned to the top with the slack below it, because a one-line box stretched down a tall card reads as a mistake. |
