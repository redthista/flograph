# Known issues

7. ~~CTD on Linux/Wayland while locking a page and then dragging a Plotly chart, with the app going sluggish just before it died~~ — root-caused and fixed. The core dump was a **hover event inside the chart card's embedded Chromium** (`QQuickWidget` → `QQuickDeliveryAgent::deliverHoverEvent`) being routed through `QCoreApplicationPrivate::sendThroughApplicationEventFilters` into PySide, which segfaulted in `PySide::getWrapperForQObject`. The page tab's context menu (`ui/dashboard/page_bar.py`) installed an event filter on the **QApplication** so it could swallow the context-menu event the platform sends on release after the menu was already opened on press. Two faults compounded: (1) an application-wide filter sees *every* event in the process, so each mouse-move and hover inside WebEngine had to be handed to Python — that is the sluggishness, and the crash site; (2) the filter object was a module-level `QObject` constructed at **import** time, before `QApplication` exists (`app.py` imports `MainWindow` before constructing the application), which is precisely the state PySide's wrapper bookkeeping is not safe in. A third, latent: the filter was removed by a `QTimer` parented to the tab bar, so a page bar destroyed before it fired left the filter installed for the rest of the session. All three are gone — `PageTabBar.contextMenuEvent` accepts the event on the one widget it is delivered to, which is the documented way to do this and needs no timer, no global state and nothing to leak. Regression tests: `tests/test_page_bar_context_menu.py`, which pins the *mechanism* (no `installEventFilter` anywhere in the module, no import-time QObject) as well as the behaviour, because the fix is a deletion and a deletion is easy to reinstate by accident.

## 1. Flaky test-suite crash at process exit (~25% of runs, pre-existing on master): `double free or corruption` / `QBasicTimer::stop ... different thread` abort during garbage collection. Repro: run `tests/test_show_plot_node.py tests/test_show_table_node.py tests/test_view_keyboard.py` together a few times (offscreen). Involves jedi completion threads (spawned via the editor dock in MainWindow tests) still running while Python GC tears down Qt object cycles; tests themselves all pass — the crash is in teardown. Likely fix directions: shut down jedi/completion threads in MainWindow close, or break Python reference cycles through QWidgets so their teardown doesn't depend on the GC.

4. ~~i had an issue where i added a column to an established flow, and i had an output that was supposed to take from that new col, but it seemed the cache wasnt updating even when resettingthe whole cache~~ — root cause found and fixed for the "reset cache and rerun everything wipes the column" half: F5/Run Selected/Reset Caches/the run-node context-menu actions all read `node.params` synchronously (`_start_node`, `engine/scheduler.py`), but Qt only commits a Table cell's open editor into the model on Tab/click-away/FocusOut — never on those actions themselves. Type a value, then hit F5 or Reset Caches before clicking off the cell, and the run reads the *old* `data` param; a linked Table's `merge_linked_sheet` (`core/sheet/engine.py`) then sees an all-blank user column and silently drops it as "no work worth carrying" — matching "clear cache and rerun everything removes the values I put in." Fixed by `MainWindow._flush_pending_edits()` (blurs a still-open grid editor via `_focused_spreadsheet()`), called at the top of every run/reset entry point. The dirty-propagation/caching machinery itself was checked closely and is sound — an upstream edit does correctly dirty its whole downstream chain. Separately investigated but unresolved: the "ran the Plotly chart and it just sat in Running forever" symptom — no deadlock found in the scheduler itself (`ExecutionEngine.run_targets` is a guarded no-op if a run is already active, consistent with a second click doing nothing), but there's no timeout/watchdog on a stuck worker either, so a genuine hang in a downstream node (chart rendering, a native call) would look exactly like this and has no repro to chase further. Flag it again if it recurs now that the data-loss half is fixed.
5. ~~CTD (crash to desktop) on Windows: `libshiboken: Internal C++ object (QVBoxLayout) already deleted`, raised from inside a `QUndoCommand::redo()` while editing a dashboard tile's sheet, and separately from `ExecutionEngine._on_node_finished`~~ — fixed. 6. ~~A newly-added column shows populated upstream but empty in a downstream Filter's "filtered" output; deleting the cache folder and re-running reproduces it exactly~~ — root cause found and fixed. Node outputs are cached and handed downstream *by reference*, and the node contract ("treat inputs as read-only") was documented in five places but enforced nowhere. A script node doing the natural thing — `table["pattern"] = ...`, `df.loc[:, col] = ...`, `rename(inplace=True)` — was writing into the entry cached against the node upstream. Under pandas 3.0 copy-on-write that is silent instead of loud: a branch that took its copy *before* the write keeps the old block, so the Filter's "filtered" holds the column as it was when the Filter ran (empty) while the upstream value the user inspects as "all data" holds the written version. No error, no stale cache, and clearing the cache changes nothing — execution order is deterministic, so every re-run reproduces it. Fixed in `engine/scheduler.py`: `_read_only_view()` hands each node its pandas inputs as a copy-on-write shallow copy, which shares every block (fifty over a 16 MB frame cost 0.09 MB) but copies on first write, so the write stays local to the node making it. `_alias_source` now matches against what was handed in, keeping the pass-through/link-chain memory sharing from 0.1.8 intact. Non-pandas values (list, dict, numpy array) have no equivalent free guard and are still read-only by contract only. Regression tests: `tests/test_input_isolation.py` (four in-place idioms, each of which corrupts the upstream cache without the fix).

8. **Still a restore-from-cache bug in larger flows** (Dan, 0.1.13). Reported without a repro, and it needs one before it is chaseable — issues 4 and 6 were both "the cache is wrong" and both turned out to be something else entirely (an uncommitted grid editor; a node writing into its input), so the label is not evidence about the cause. What would make it actionable: which node comes back wrong, whether it comes back *stale* or *empty*, whether the flow was reopened or only re-run, and whether the node's own cache entry is on disk at all. Where to look once there is one: `engine/cache_persistence.py` writes one blob per node plus a `cache/manifest.json` keyed by `node_fingerprint`, and it is deliberately forgiving — an unpicklable output, a mismatched fingerprint or a corrupt blob all **skip that entry silently** and the node loads dirty (four separate `except Exception: skip` sites). Silent-skip is right for one bad node and is exactly what would hide a systematic failure on a big flow, so the first move is to make the skips *reportable* — a count, or a line in the console naming what did not come back and why. That is worth doing whether or not it finds this bug. Suspects worth ruling out with a large flow to hand: the recursion-limit guard on fingerprinting deep graphs (`node_fingerprint` uses an explicit stack for exactly this reason), the alias/pass-through restore (`restore_aliases` — a source that was skipped leaves its whole alias chain dirty), and memory pressure (`engine/pressure.py`) dropping entries before they are written.

9. ~~A second, unasked-for context menu opens after using one of the page bar's menus~~ (Dan, 0.1.14, Linux/Wayland) — found and fixed. Right-click the **Model** tab, click *Fold the canvases away*, and a stray menu appeared, holding a lone "New Group…". It is the family of issue 7 and the AB4 Wayland trap: the context event a right **press** brings is delivered to the widget with **focus**, and only after the handler that opened our own menu has returned, so it lands on whatever had focus and opens *that* widget's menu. `PageTabBar._menu_with_the_focus` (focus to the bar either side of the menu) plus `PageTabBar.contextMenuEvent` swallowing the follow-up is the existing defence, and it is evidently not covering this path. A lone "New group…" is exactly what `LibraryTree._on_context_menu` builds on empty space, so the Node Library dock was the first suspect and now ignores a request whose position is not on the tree (`_context_menu_for`, regression test in `tests/test_library_components.py`) — but Dan still sees the menu after that guard, so either the delivered position lands *inside* the tree (the dock sits directly under the bar, so bar coordinates can fall in it) or the menu is somebody else's. **It was the first of those.** The page bar sits along the *top* of the window and the Model tab is its leftmost, so the menu it opens drops straight over the Library dock: when the fold entry is clicked, the pointer is over the tree, and the leftover context event arrives at a position that is genuinely *on* it. No geometric guard can tell that event from a right-click made there — which is why the position check fixed nothing, and why chasing "whose menu is it" was the wrong question. Anything sitting under one of the bar's menus can answer it: the Library tree's lone "New group…", a Paste over a dashboard, the canvas's add-node palette, the window's own dock list. **The fix is timing** (`ui/menu_guard.py`, ~35 lines of module-level float and two functions): the page bar records the moment one of its menus closed — every one of them goes through `_menu_with_the_focus`, and `+` now does too — and each surface that can be underneath refuses a context menu for `SETTLE` (0.35s) afterwards. Nobody right-clicks a third of a second after dismissing a menu; the leftovers arrive in milliseconds. The keyboard's Menu key and any event that is not `spontaneous()` are never refused. Deliberately no QObject and no event filter, least of all on the application — that was issue 7's segfault, and `tests/test_page_bar_context_menu.py` pins its absence. Belt fastened on seven surfaces (Library tree, canvas view, dashboard view, dock host, data table, sheet column and row headers); regression tests in `tests/test_stray_context_menu.py`, including a source check that each one still asks, because the next widget added is the one that will forget.
