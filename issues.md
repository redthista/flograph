# Known issues

7. ~~CTD on Linux/Wayland while locking a page and then dragging a Plotly chart, with the app going sluggish just before it died~~ — root-caused and fixed. The core dump was a **hover event inside the chart card's embedded Chromium** (`QQuickWidget` → `QQuickDeliveryAgent::deliverHoverEvent`) being routed through `QCoreApplicationPrivate::sendThroughApplicationEventFilters` into PySide, which segfaulted in `PySide::getWrapperForQObject`. The page tab's context menu (`ui/dashboard/page_bar.py`) installed an event filter on the **QApplication** so it could swallow the context-menu event the platform sends on release after the menu was already opened on press. Two faults compounded: (1) an application-wide filter sees *every* event in the process, so each mouse-move and hover inside WebEngine had to be handed to Python — that is the sluggishness, and the crash site; (2) the filter object was a module-level `QObject` constructed at **import** time, before `QApplication` exists (`app.py` imports `MainWindow` before constructing the application), which is precisely the state PySide's wrapper bookkeeping is not safe in. A third, latent: the filter was removed by a `QTimer` parented to the tab bar, so a page bar destroyed before it fired left the filter installed for the rest of the session. All three are gone — `PageTabBar.contextMenuEvent` accepts the event on the one widget it is delivered to, which is the documented way to do this and needs no timer, no global state and nothing to leak. Regression tests: `tests/test_page_bar_context_menu.py`, which pins the *mechanism* (no `installEventFilter` anywhere in the module, no import-time QObject) as well as the behaviour, because the fix is a deletion and a deletion is easy to reinstate by accident.

6. ~~A newly-added column shows populated upstream but empty in a downstream Filter's "filtered" output; deleting the cache folder and re-running reproduces it exactly~~ — root cause found and fixed. Node outputs are cached and handed downstream *by reference*, and the node contract ("treat inputs as read-only") was documented in five places but enforced nowhere. A script node doing the natural thing — `table["pattern"] = ...`, `df.loc[:, col] = ...`, `rename(inplace=True)` — was writing into the entry cached against the node upstream. Under pandas 3.0 copy-on-write that is silent instead of loud: a branch that took its copy *before* the write keeps the old block, so the Filter's "filtered" holds the column as it was when the Filter ran (empty) while the upstream value the user inspects as "all data" holds the written version. No error, no stale cache, and clearing the cache changes nothing — execution order is deterministic, so every re-run reproduces it. Fixed in `engine/scheduler.py`: `_read_only_view()` hands each node its pandas inputs as a copy-on-write shallow copy, which shares every block (fifty over a 16 MB frame cost 0.09 MB) but copies on first write, so the write stays local to the node making it. `_alias_source` now matches against what was handed in, keeping the pass-through/link-chain memory sharing from 0.1.8 intact. Non-pandas values (list, dict, numpy array) have no equivalent free guard and are still read-only by contract only. Regression tests: `tests/test_input_isolation.py` (four in-place idioms, each of which corrupts the upstream cache without the fix).

8. **Cached results don't survive a flograph upgrade on larger flows** (Dan, 0.1.13 — reported as "still a restore-from-cache bug in larger flows"). Investigated 2026-09-12 against saved flows of Dan's: three causes, two of them fixed.

   **Fixed — a save made during a run restored old values.** `_start_project_save` planned a *carry-all* save whenever `engine.active`: the graph was written, but every blob *and its manifest entry* was copied from the file being replaced, and the undo stack was then marked clean. A node re-run since that file was written — Reset Caches, or a source whose data changed, same params — went back in with its old value under a fingerprint that still matched, so reopening served the old table as current and quitting never asked. Reproduced headless (`NEW` in the session, `OLD` on reopen). The carry-all path is gone: a mid-run save snapshots the live cache like any other, which is safe because the GUI thread owns the cache and a node dirtied for a re-run was evicted at that moment, so it is simply absent (`TestSaveDuringARun` in `test_project_bundle.py` and `test_saving_progress.py`).

   **Fixed — silent.** Opening says what did not come back and where it starts (`cache_persistence.restore_report`, on the "Opened…" line: *"11 node(s) restored from cache · 25 out of date and will re-run, starting at Update, Report Date"*); a blob that will not read back is counted on the same line; a result a save cannot store is named in a corner notice, once per node per session (`write_project(skipped=)`).

   **Fixed — a node that wrote into its input came back without the write** (found by Dan testing the two fixes above, 2026-09-12; on master too). `_alias_source` recognised a pass-through by identity against the copy-on-write copy it had handed in, and a Python Script doing `df['year'] = ...; return in1` hands back that same copy — so `Add Year Column` was recorded as an alias of `Sort`, with no blob of its own, and a reopen rebuilt it from `Sort` (21 columns, no `year`), leaving the `Report Date` slicer green with no values. The engine now records the copy's storage and labels as it is handed in (`_input_token`) and aliases only if the node gave it back untouched (`_untouched`: identity of the block manager, blocks and axes plus names and attrs; the items, for a list or dict) — 0.1 ms for a 128 MB frame, 2 ms for a 200k-row list, and correct for 25 of 25 read and write idioms checked. Files already saved that way heal on open: an alias whose recorded columns differ from its source's is not restored (`_alias_matches_source`), so the node re-runs — and so does every link registered through it, since an alias is now registered only once its source has been (left in, they counted as done with nothing to load, which kept the restore bar up for good). A card that shows its inputs — Slicer, control, linked Table, report — whose own node is already clean now refreshes when a node feeding it succeeds (`MainWindow._on_upstream_node_succeeded`): before, it refreshed only on its own run, which a clean node never gets.

   **Not fixed — an upgrade throws away the cache below any node whose script changed.** The fingerprint hashes a node's `source` (for a builtin, the builtin's own script) and its `params` (defaults filled in on load), folded into everything downstream. Opening `dc_test.flograph` (saved 2026-08-30) restores **11 of 36**: its Slicer and Action Button changed, and the 23 results below them go too; a second flow restores 11 of 14. Rebuilding the hash by hand matches the manifest only with the *old* script and the *old* params. 44 of the 118 builtin scripts changed between v0.1.13 and now (30 in 0.1.12, 8 in 0.1.13) — and, the measurement that rules out the obvious fix, **none** of the 44 changed only in comments, docstrings or layout, while a new param always edits the script as well. So normalising the hash (strip comments, drop default-valued params) would recover nothing and would invalidate every existing cache once. What would work is **early cutoff**: re-run the changed node and, if its output is identical to what the file held, keep everything below it — a Slicer re-runs in milliseconds and its 23 dependants would come back. That is a design, not a patch: it needs an output digest that is content-stable (a pickle's bytes are not — equal values can pickle differently; `pd.util.hash_pandas_object` for frames, something else otherwise), a place for a provisionally-valid entry to wait until its changed parent has re-run (scheduler dispatch), and a bound on the cost of hashing a large output after a run (only worth paying for a node with a provisional dependant). Decide it before building it. Running from master makes this bite far more often than a release does: every update that touches a node script does it.

9. ~~A second, unasked-for context menu opens after using one of the page bar's menus~~ (Dan, 0.1.14, Linux/Wayland) — found and fixed. Right-click the **Model** tab, click *Fold the canvases away*, and a stray menu appeared, holding a lone "New Group…". It is the family of issue 7 and the AB4 Wayland trap: the context event a right **press** brings is delivered to the widget with **focus**, and only after the handler that opened our own menu has returned, so it lands on whatever had focus and opens *that* widget's menu. `PageTabBar._menu_with_the_focus` (focus to the bar either side of the menu) plus `PageTabBar.contextMenuEvent` swallowing the follow-up is the existing defence, and it is evidently not covering this path. A lone "New group…" is exactly what `LibraryTree._on_context_menu` builds on empty space, so the Node Library dock was the first suspect and now ignores a request whose position is not on the tree (`_context_menu_for`, regression test in `tests/test_library_components.py`) — but Dan still sees the menu after that guard, so either the delivered position lands *inside* the tree (the dock sits directly under the bar, so bar coordinates can fall in it) or the menu is somebody else's. **It was the first of those.** The page bar sits along the *top* of the window and the Model tab is its leftmost, so the menu it opens drops straight over the Library dock: when the fold entry is clicked, the pointer is over the tree, and the leftover context event arrives at a position that is genuinely *on* it. No geometric guard can tell that event from a right-click made there — which is why the position check fixed nothing, and why chasing "whose menu is it" was the wrong question. Anything sitting under one of the bar's menus can answer it: the Library tree's lone "New group…", a Paste over a dashboard, the canvas's add-node palette, the window's own dock list. **The fix is timing** (`ui/menu_guard.py`, ~35 lines of module-level float and two functions): the page bar records the moment one of its menus closed — every one of them goes through `_menu_with_the_focus`, and `+` now does too — and each surface that can be underneath refuses a context menu for `SETTLE` (0.35s) afterwards. Nobody right-clicks a third of a second after dismissing a menu; the leftovers arrive in milliseconds. The keyboard's Menu key and any event that is not `spontaneous()` are never refused. Deliberately no QObject and no event filter, least of all on the application — that was issue 7's segfault, and `tests/test_page_bar_context_menu.py` pins its absence. Belt fastened on seven surfaces (Library tree, canvas view, dashboard view, dock host, data table, sheet column and row headers); regression tests in `tests/test_stray_context_menu.py`, including a source check that each one still asks, because the next widget added is the one that will forget.
