11. Scroll the canvas when a connection is dragged to its edge (was ideas.md G3, from Stu via KNIME). Shipped 2026-08-25. Holding whatever is being dragged against a viewport border now pans the canvas that way until the destination arrives — a wire's free end, a node, a multi-selection, a frame with its contents — no letting go, no panning, no starting over. The scene announces a canvas drag (`NodeGraphScene.canvas_drag_changed`, with `wire_drag_active` / `group_drag_active` / `canvas_drag_active` to read it; group drags count nesting depth so commit's nothing-moved early return can never strand the announcement), and the view runs a tick timer for the duration: each tick asks `edge_scroll_delta` — a pure function of viewport rect and cursor, band per axis, faster the deeper into the band — pans by it through `scroll_by` (the same translate math as a middle-drag pan), then re-aims what is in hand. The timer also stops itself if it ever fires without a drag under it, so nothing can strand it scrolling forever. Frame pins are real PortItems and drag-detach reuses begin_wire_drag, so collapsed frames and grabbed wires edge-scroll without a line of their own.

13. Nodes and frames that run only when asked (was ideas.md J1 + J2). Shipped 2026-08-25, one commit (`c4f1552`). A `manual` flag on `NodeInstance` (beside `active`/`locked`/`frozen`, right-click ▸ Run only when asked) takes a node out of every run that does not name it: Run All walks past it and so does the re-run a moved slider sets off, while Run To This Node, Run Selected and an Action Button naming it still fire. Not a third spelling of deactivate — a manual node **holds its place and whatever it last produced stays available downstream**, like a frozen value, so the dashboard under an expensive query keeps working off the last answer; only a manual node that has produced nothing yet skips the branch below, there being no input to run on. 15. A manual run during a run joins the one in flight (was ideas.md J3, from Stu). Shipped 2026-08-25, after one false start. `ExecutionEngine.run_targets` was a hard no-op while a run was in flight, so clicking Run on anything during a long run did nothing at all — no message, no result, a click into the void. The first cut parked manual runs behind the current one, reusing the reactive path's survive-and-drain trick; putting it in front of Dan ended that immediately — *the engine already runs independent branches side by side, the second click should too* — and he was right: queueing answered "the click did something" while leaving the actual complaint (why can't they run together?) standing. So: **join the plan**. `_join_targets` builds the plan exactly as a fresh run would (same closure, same flags, `asked` intact for the manual-node rule) and subtracts what the run already owns — in flight, already queued, or finished-and-clean, which build_plan skips on its own — then seeds the remainder into the same Kahn bookkeeping with predecessor counts taken across the *extended* plan, so a joined node downstream of an in-flight ancestor waits on it via the ordinary completion path, and an upstream failure prunes it via the ordinary prune. The progress total grows as joins land; each start reports the total as it stands when it starts. Warming was the one real trap: a join arriving while spilled cache is still being read back starts a second warm, so the per-run `_warm_remaining` counter became a per-generation dict — the first warm finishing must not dispatch while the second is still out, and the old single-generation check would have silently dropped its own callbacks and hung the run. Cancel takes joined nodes back off like planned ones. The status bar says "N nodes joined the running plan" (`run_joined`); the canvas says the same with queued-then-running lights. Tests: `tests/test_run_during_run.py`.
16. Saving, cache and disk (was ideas.md chunk K: K1 progress while saving, K2 disk warnings, K3 compressed cache pickles). Shipped 2026-08-26, one commit, and the three really are one story: a big flow filling or exhausting the disk without saying so. **K1** — the side-car half of a save pickled every cached result out on the UI thread, seconds to minutes of frozen window reading as a hang; the save is now split the way the load already was (`cache_persistence.plan_cache_save` snapshots ids/entries/fingerprints/frozen-flags cheaply on the GUI thread, `write_cache_plan` touches only the snapshot and the filesystem on a pool thread via a new `CacheSaveRunnable`), with a second hairline bar beside the run bar counting `cached results 12/40` in the status line. Until it lands: a second Save waits with a word, **Save As checks before moving `_project_path`** (refusing after the move would leave the project aimed at a file never written), **all four manual-run entries hold off** (a run would dirty the entries being walked), and **closeEvent sees the write out** — a manifest never written throws away everything just saved. **K2** — nothing anywhere checked free space; the resource monitor now watches the project's drive (`set_disk_watch_path`, updated at open/save-as/new/example) and announces under 1.5 GB free once, amber like memory pressure, with hysteresis (`pressure.disk_is_low`, same LOW_FREE figure as memory so one number means one thing), carried onto the run line like the memory note instead of being overwritten mid-run, plus a tooltip line; and a failed *save* is now a sentence — `save_failure_text` turns ENOSPC/EDQUOT into "The disk holding … is full", shared by both halves so the wording cannot drift between threads (the JSON half catches OSError into a dialog; the pool half lands its error text in `finished`). Per-blob unpicklable failures still skip silently as ever — whole-save failures speak, one bad node does not. **K3** — measured before choosing, as the idea demanded: zlib 1/6/9 and lzma-1 over float-heavy and string-heavy frames; strings (most of what caches hold) fell to ~40% of raw at level 1 for ~8% of pickle time, floats shrank for nobody, level 9 had a 9-second outlier, lzma read back 4× slower — so **zlib level 1**, streamed through a `_ZlibSink` so the biggest blob never doubles in memory. The setting Dan asked for (**Settings › General › Saving › Compress cache**, default on) applies at the next save; backwards compatibility is absolute because `load_blob` sniffs each blob (pickle protocol 2+ always starts `\x80`, a zlib stream never does) rather than trusting the manifest — old raw side-cars, compressed ones, and any mix load forever, no migration. Manifest bumps to schema 3 with a per-entry `codec` field for self-description (old builds reject the schema cleanly rather than choking mid-unpickle). Also swept stray `.pkl.tmp` crash leftovers that the `*.pkl` glob could never match.
    Follow-up the same day, from testing on Bazzite: the drive watch read nothing there — `Path.anchor` collapses every Unix path to `/`, and on an immutable distro `/` is the small ostree system root while `/home` (a bind of `/var/home`) is its own filesystem, so asking at the anchor measured a mount that was never the project's. Fixed by keeping the full path and probing free space **at the project's own folder** (`_drive_label` picks the longest matching mount point from psutil for the label; shutil with a psutil fallback for the reading). And Dan asked the hover to show what compression bought: `_ZlibSink` now tallies bytes in and out as they stream by, the manifest records both per entry (`raw_bytes`/`disk_bytes`, no uncompressed copy ever held just to measure), carried-over blobs record disk-only, and `sidecar_stats()` sums it into the monitor's tooltip line — `Cache on disk 412 MB · 1.02 GB uncompressed (41%)`.

The note asked for a fixed set of optional ports (2 visible, up to 8 declared), honouring the 2026-08-18 lesson that data-grown ports were rejected as against the grain — so the first build declared *third* … *eighth* as optional ports the run uses when connected. 21. Scale a dashboard page to fit the window (asked directly 2026-08-27; now N2). Shipped the same day, after an estimate rather than a guess — the pieces all existed, so the honest answer was "half a session, and the risk is not the code". **Scale to fit the window**, on the page tab's menu beside *Locked*, zooms the page on every resize so the same tiles stay framed, instead of a bigger window revealing empty canvas around them: the screen a dashboard is opened on is rarely the screen it was built on. Per page and saved with the project, mirroring `view_mode` line for line — the flag on `Page`, a setter that treats False as a decision rather than silence, a command, the tab menu's tick, and the window driving the widget from the model so undo and a project load take the same road. Independent of the lock, so a page still being built can scale too; the two share one navigation lock and neither may clear the other's. Hand zoom and pan go off while it is on — they would only fight the next resize, and "why did my zoom snap back?" has no good answer — and the zoom indicator says why. The refit waits for a window drag to finish rather than firing on every step of it, holds off while a tile is maximized (that one is pinned to the viewport; refitting under it would only slide it off), and follows a tile that moves. Two things the tests caught rather than eyes: `fitInView` answers with whatever ratio the arithmetic gives it, including one no other zoom in the app may reach, so it is clamped back to the same 400% ceiling; and a tile dragged to the far edge was fitted to and then not reached, because the scrollable span is recomputed on a debounce — the same flush the wheel work needed. The trade-off to know about, and the reason it was worth trying before deciding: at a fitted zoom, painted things (KPIs, charts, PDF pages) re-render at the new scale and stay crisp, while a data table or a spreadsheet is a raster widget being scaled and reads a little softer than at 100%. Dan tried it on a real dashboard before it landed. Not offered on report pages, which already sit on a page of a declared size. Tests: `tests/test_page_scale_to_window.py`.
