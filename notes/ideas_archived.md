6. Manual apply mode for tables and controls. A per-node (or global) toggle switching a Table / slicer / input control between re-running downstream on every edit (today's behaviour, now coalesced into one run per burst — 0.1.8) and only running when an **Apply** button is clicked. For flows heavy enough that no amount of debouncing helps: batch a dozen edits, then commit once. Mechanically small — the SetParamCommand already dirties the subgraph whether or not anything runs, so it is a param, a button that lights when there are edits the flow has not seen, and an early return in `_on_dashboard_sheet_edited`. The open question is the badge: amber STALE currently means "you changed something, run when ready", but under manual apply it becomes that table's normal working state and would need to read as an invitation to click Apply rather than as a warning. Shelved 2026-08-03 — revisit if the 300ms coalescing turns out not to be enough.

8. Reports — HTML export via Jinja (was ideas.md chunk B, "BIG ONE"). A *second* export target alongside the PDF one, not a replacement, agreed 2026-07-26. Why it was worth it: real CSS — `@page`, `@media print`, forced breaks, `page-break-inside: avoid` (keeping a chart off a page boundary, which Qt cannot express at all), running headers and footers with counters; web fonts, flexbox/grid; Plotly staying **interactive**; browser print-to-PDF for anything designed. Most of the groundwork already landed and is not part of the remaining cost: `core/html.py` (Qt-free coercion), `ui/browser.py` (writes a named page to a session temp dir and hands it to the desktop), `core/page_setup.py` (the geometry, with `page_css()` already emitting the `@page` rule), and `ui/report/html.py` (a rendered report as one self-contained HTML file, charts inlined as data URIs, animations kept as the GIF/WebP they arrived as). What is genuinely left is the **template**: Jinja, a stylesheet the user can replace plus a code node that injects CSS, `@media print`, running elements with counters, and keeping Plotly interactive rather than snapshotting it. Carries with it **B1, a preview that can show either target** (asked for 2026-08-12, after the first look at Save HTML): a target dropdown on the report toolbar — *Pages* (today's paged preview, what the PDF will be) and *Web* (a QWebEngineView of the exported HTML). The view itself is cheap since the app already embeds Chromium for the Plotly snapshotter, but it needs the template to exist first or it previews a page nobody would ship. Cost to be honest about: today the preview and the PDF are literally the same QTextDocument and cannot disagree; with a browser round trip the preview becomes an approximation and "open in browser" becomes the real preview. 0.1.9 narrowed the gap rather than closing it — the exported HTML now carries the page's own `@page` size and margins and measures its body to the same text column, so it prints sensibly from a browser, but it is one continuous page rather than a stack of sheets and always will be. One original argument has evaporated: "and it needs no kaleido" stopped being true when 0.1.8 started snapshotting Plotly through the embedded Chromium, so the PDF path needs no extra library either — the CSS and pagination arguments stand on their own, this is just a smaller win than it looked. Shelved 2026-08-12. **Update 2026-09-29:** the interactive half landed without the template — `ui/report/live.py` splices live Plotly and browser tables (sort, fold groups, `|search`, tooltips) into Qt's HTML after the fact, keyed by `embed:N` and the table marker; opt-in per embed with `|live`. What is left of item 8 is the layout half only: Jinja, running elements, counters.
14. Pan by holding right-click (was ideas.md G1) — built, tried, taken back out. Attempted 2026-08-25 and reverted the same day at Dan's request, after trying it for real. What shipped first was a threshold design: a right-press held for judgement in `ZoomPanGraphicsView`, past a few pixels of travel it became a pan and armed `_suppress_context` to swallow the menu Qt synthesizes from its release. Two lessons from putting it in front of someone: **the platform matters** — on his desktop Qt synthesizes the context menu from the right-button *press*, so the menu won every time before the threshold could; the fix (capture the press-time menu event while pending, re-issue it manually on release if the gesture stayed a click, swallow it if not) was designed but never needed. And **the shape of the setting was wrong**: he had expected a picker of pan buttons (left/middle/right), not a toggle — left would have collided with node-dragging and rubber-band selection and needed its own decision. Rather than grow it, he changed direction entirely: what he actually wanted was visible scroll bars. That shipped instead — **Settings › Canvas › Display › Show scroll bars**, `ZoomPanGraphicsView.set_scrollbars_enabled()` flipping both axes between `ScrollBarAlwaysOff` and `ScrollBarAsNeeded`, pushed to the main view and every dashboard view (`canvas/scrollbars`, off by default). G1 stays here as declined-by-user rather than open: if it ever comes back, start from the press-time menu lesson above.
15. Auto-drop under memory pressure. When the machine is critically short of memory during a run (`engine/pressure.py` already reads it once a second), treat intermediate nodes as if Drop Output were on for the rest of that run: a value goes as soon as nothing left in the run reads it. Mechanically small, because it rides the existing Drop Output machinery — `scheduler._hold/_consumed/_release` drop it, `released` marks it, `build_plan._with_released` brings it back when a later run or an aimed run needs it. Would exclude frozen nodes, aimed nodes and nodes whose card or tile is showing (a card holds its own reference, so dropping the cache entry frees nothing there anyway). The trade it makes: an edit downstream later re-runs the upstream chain instead of reading the cache — compute instead of swap. Raised 2026-10-06 investigating a 500+ node flow at ~29 GB on a 16 GB machine; Dan's call: not now — users choose what to drop via the existing per-node Drop Output, and a slow run on big data is fine as long as the window stays responsive. The larger sibling, a budgeted LRU spill to disk, is still the known next step if memory pain recurs (needs calibrated sizes first: `estimate_size` is a footprint, not RSS).
16. Open and save `.xlsx` in the Table — a Table that behaves like a workbook you can open, work in and save back. Nearly everything the Table stores has an Excel twin: values and A1 formulas (`[@Col]` is Excel's own structured-reference syntax), number formats, bold/italic/underline/fill/font colour/alignment/wrap, notes (Excel comments), named ranges (defined names), freeze panes, hidden rows and columns, row heights and widths, outline groups, dropdowns and validation, conditional-formatting presets (not custom rules). What doesn't map: a Table is one sheet with a header row and typed columns, so opening picks a sheet and confirms the header row; formulas outside our function set or reaching other sheets come in as their cached values with a note on the cell; merged cells, charts, pivots and macros have nowhere to land. **The trap is saving back:** openpyxl drops what it doesn't understand (charts, images, pivots, slicers) when it rewrites a file, so Save As a new `.xlsx` is always safe, but writing over the source must first check the workbook holds nothing openpyxl would lose, and say what would go. Plan: phase 1 Open `.xlsx` into a Table + Save As `.xlsx` (round-trip test: export, reopen, compare); phase 2 a Table linked to its workbook — remembers the path, offers to reload when the file changes, Save writes back behind that guard. openpyxl is already in the `excel` extra (Read/Write Excel nodes move values only). Absorbs "export to .xlsx with formats". Shelved 2026-10-10 by Dan's call, in favour of the small batch (selection summary, AutoSum, F4).
17. Protect cells in the Table — lock the formulas, leave the inputs open. Excel's *Format Cells ▸ Locked* + *Review ▸ Protect Sheet*: a Table handed to someone on a dashboard is only safe when they can type into its input cells but cannot overwrite a formula by accident. Shape: a `locked` flag on cells or whole columns, kept look-only like the other per-cell formats (`presentation` paths, so locking re-runs nothing); a Protect toggle on the Review tab; typing into a locked cell is refused with a note saying why (the Stop-rule refusal path already exists); the builder can always unlock. Fits the product vision (live dashboards for non-technical users) better than anything else left. Medium. Shelved 2026-10-10.
